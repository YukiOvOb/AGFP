## 2026-10-15 Migration, read fields, demo data

### What was built

- **Migration V005** (`app/src/main/resources/db/migration/V005__equipment_master_data.sql`), additive:
  - `serms.equipment_category(name, created_at)`, backfilled with the existing free-text categories. `equipment.category` references it: a rename cascades to the equipment, deleting a category that is in use is refused.
  - On `serms.equipment`: `serial_number` (unique, blank refused), `description` (blank refused), `condition` (`GOOD` / `FAIR` / `POOR`, default `GOOD`), `max_borrow_duration` (interval, must be positive; NULL means the global reservation limit).
- **UC01 read fields**: search results and the `equipment` object of the availability response carry `description` and `maxBorrowDuration` (ISO-8601, nullable). - **Demo data**: `scripts/demo-data.sql` fills serial numbers, descriptions and maximum durations (camera 3 days, projector 2 days, laptop 5 days) for the demo items, only where still unset.
- Also corrected two texts from the D-012 record that assumed the owner's pronouns.

### Design notes

- **Backfill rules.** Serial numbers were never recorded, so existing rows stay NULL ("not recorded") instead of receiving invented values; PostgreSQL's unique constraint allows several NULLs. Existing items are in service, so their condition starts as `GOOD`.
- **Condition is wear, not faults.** There is no `DAMAGED` value: a fault opens a maintenance case (UC04), which already controls availability.
- **Categories by name.** The free-text column stays and becomes a foreign key to the category name, so every existing query keeps working and a rename is one `UPDATE` on the category.
- **Compatibility trigger.** The local demo seed and the UC01, UC03 and UC04 PostgreSQL fixtures insert equipment with free-text categories. A `BEFORE INSERT OR UPDATE OF category` trigger registers an unknown category instead of failing. The management API in #17 should still validate a chosen category against the list.
- **Interval in the database, ISO-8601 in the API.** PostgreSQL accepts ISO-8601 input (`'PT48H'`), the read model converts the interval to whole seconds (`EXTRACT(EPOCH ...)`) and the API sends `Duration.toString()` (for example `PT51H`), the same style the maintenance report uses for durations.
- **Test bench follows the real sequence.** `SermsPostgres` used to apply only V001 and V002 as a historical UC01 bench. The search query now reads V005 columns, so the bench applies every migration in order, the same sequence Flyway runs.
